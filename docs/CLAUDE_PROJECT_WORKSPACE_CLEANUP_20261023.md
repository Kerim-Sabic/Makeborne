# Claude task: simplify Makeborne's project workspace

## Goal and ownership
Make opening a project feel as clear and focused as the observed Lovable editor while preserving Makeborne's identity and working features. Improve information hierarchy, not only spacing. This is a separate UI change after the narrow composer/account-history release. Read the latest docs/AGENT_HANDOFF.md before touching files. Record your branch/base, file ownership, behavior changes, tests and handback there. Coordinate overlapping live-builder, cloud-studio and preview changes with Codex. Do not deploy, merge to main, change production settings, enable features, spend on AI/cloud services, or change billing/auth/database contracts under this task. Keep code on a feature branch from the actual latest main after the approved release. Preserve unrelated worktrees and uncommitted work.

Read docs/release-review/lovable-deep-ux-review-20261020.md, lovable-design-system-measurements-20261020.md, lovable-history-retrieval-20261020.md and lovable-comparison-20261022.md. ## Concrete problem
The current screen stacks editor-heading/cloud-workbench-heading, status badges, workbench-toolbar/cloud-workbench-tabs, preview/device controls and route selection. Saved version, build/check state, publishing state and preview version compete with project title and Save. On phones the stacked metadata consumes the space intended for the product preview. The user should immediately understand which project is open, whether work is saved, how to request/edit a change, and where to preview or publish.

## Proposed hierarchy to implement and qualify
1. One global project header. Left: Back to projects and a project-name dropdown; no duplicate generic workspace title. Center or adjacent: one truthful save indicator. Right: one primary Publish action when appropriate, plus an overflow menu. Default desktop header target 52–56px. The project menu holds type, version, current publication address/state, rename and project actions that already exist. Avoid adding unavailable actions.
2. One preview toolbar immediately above the canvas, target 40–44px desktop. Group Preview and the relevant editor view (Code for full-source websites, Content for documents). Keep device controls and a compact route selector in this bar. Put History, client review, source export and less frequent tools in clear menus or one existing panel navigation; do not expose the same action in two rows. Choose the placement after inventorying actual usage and consequences.
3. Chat stays in the left pane on desktop and in the existing phone conversation sheet. Its composer stays the qualified clean version: attachment button, Build/Plan when supported, effort, send/stop and optional Request details. Do not reintroduce informational paragraphs or hide actual errors, stop/recovery controls or authorization needs.
4. Primary Publish opens the publishing workflow; it must not immediately publish, bypass approvals or imply a site is live. Save must remain independent of publication. If the app requires explicit saving, show Save changes only when meaningful; show Saved only after acknowledgment. Never invent autosave. A dirty/failed/uncertain/conflict state must remain prominent and actionable.
5. Collapse passive status chips. Saved version and preview/check metadata go in a concise project/status popover. A real running build may use a single compact progress label. Critical conflicts, expired authorizations, uncertain save outcomes, interrupted jobs and required recovery stay visible outside a closed menu. Never hide actionable failures just to meet a density target.
6. Phones: preserve preview-first layout and one reachable conversation control. Default top chrome target no more than 112px at 375px width, excluding genuinely actionable error banners. Use a compact title, truthful save state, primary action and overflow; don't wrap chips into extra rows. Touch targets around 44px, no icon-only meaning without an accessible name. At 800px avoid both desktop labels wrapping and a huge phone drawer. At 1440/2560px do not stretch the chat composer or header spacing arbitrarily.
7. Use Makeborne's neutral workspace surfaces, legible typography and restrained blue/purple accent for the single primary action. Keep selected state clear, focus visible and contrast sufficient. Avoid tiny gray labels, elaborate gradients on every control, bouncing/choreographed motion and layout shifts when text/status changes. Respect reduced motion. Use active labels/tooltips purposefully, not a row of unexplained icons.

## Keep functionality and safety
Preserve all existing website/book/deck-specific controls and capability/role gates. Reviewers must not acquire edit or publish rights. Keep unsent draft retention, account changes, pending uploads, edit locks, version conflicts, route/device selection and keyboard actions working. Preserve source asset loading so reopening does not flash a false build error. Menu actions must use current project/version identity; no stale project operations after navigation. No silent data loss when changing views, sizes or projects. Do not change billing limits, request approval, protected publishing, auth or feature flags.
